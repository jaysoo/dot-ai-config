## Vite+ (VoidZero / now Cloudflare)

> **Highest-priority section this cycle -- escalated threat.**
> **NOTE: voidzero.dev, viteplus.dev, and blog.cloudflare.com were blocked by egress policy this scan. No new Vite+ data since July 2. Status below reflects July 6 snapshot.**

**Previous status:** Alpha, watch lightly.
**Current status:** Beta (July 2, 2026), Cloudflare-backed. Active competitive threat.

### Cloudflare Acquisition (June 4, 2026)

VoidZero announced it was joining Cloudflare on June 4, 2026. All team members joined Cloudflare. Key commitments:

- **Open source maintained:** Vite, Vitest, Rolldown, Oxc, and Vite+ remain open source, vendor-agnostic, and community-driven.
- **$1M Vite ecosystem fund** committed by Cloudflare, administered by the Vite core team.
- Strategic rationale from Cloudflare: "build the future of the AI-native web." Vite integration with Cloudflare Workers/Pages/D1/R2 expected.
- The acquisition removes the startup survival risk. Vite+ now has enterprise-scale backing.

### Vite+ Beta (July 2, 2026)

**CLI:** `vp` (Vite+)
**Components:** Vite 8, Vitest, Rolldown, tsdown, Oxlint, Oxfmt + built-in task runner
**Stats:** 180+ fixes since alpha; 1,300+ public repos depend on vite-plus

Key features relevant to Nx/monorepo competition:

- **`vp run` -- Monorepo-aware task runner with intelligent caching.**
  Powered by `vite-task` (Rust, 453 stars, 548 commits), a standalone monorepo task runner that fingerprints input files to determine cache eligibility -- no explicit `inputs` configuration required. If inputs are unchanged, task is skipped instantly from cache.
- **Dependency-aware scheduling.** Workspace ordering derived from `package.json` dependency relationships, not a separate task graph config. This is a simplification vs. Nx (`project.json` targets) and Turbo (`turbo.json` pipeline).
- **`vp dev`:** Starts a dev server with HMR via Vite 8.
- **`vp check`:** Format (Oxfmt) + lint (Oxlint) + typecheck in one command.
- **Framework-agnostic, MIT licensed.** Works for CLIs, libraries, and web apps.
- No explicit monorepo config required for basic caching -- this is the differentiating DX claim.

**What `vite-task` does NOT yet have (as of July 2 beta):**

- No stable release (pre-release state); the Vite+ beta bundles it but it has no independent versioned artifact yet.
- No distributed task execution / cloud cache (analogous to Nx Cloud or Turbo Remote Cache). Not yet announced.
- No equivalent to Nx generators or Moon templates for scaffolding.

### Nx implications

**Threat level: HIGH (escalated from MEDIUM/WATCH).**

1. **The "will it survive?" concern is resolved.** Cloudflare backing eliminates the startup risk that made Vite+ easy to dismiss. It will keep shipping.
2. **Automatic input fingerprinting is a compelling DX story.** Nx requires explicit `inputs` configuration for fine-grained cache correctness. Vite+ claims to infer them automatically. If this works in practice for complex workspaces, it removes a common Nx friction point. **Recommended: evaluate vite-task's fingerprinting behavior on a mid-size Nx workspace and document where it falls short.**
3. **Vite+ targets the same "start a JS project" audience as `create-nx-workspace`.** The unified `vp` CLI (runtime + package manager + build + test + lint + task runner) is a compelling zero-config entry point. Nx's entry point requires more configuration to reach the same productivity baseline. **This is a positioning threat at the top of the funnel.**
4. **`vite-task` is Rust-based, matching Nx's own native approach.** Performance parity is plausible; benchmarks will matter.
5. **No cloud/remote cache yet.** This is Nx's window. Vite+ users who scale will need remote caching and DTE. Nx Cloud can capture that upgrade path if positioned early.
6. **Cloudflare integration risk.** Vite+ + Cloudflare Workers + Cloudflare R2 (cache storage) is a natural product bundle. If Cloudflare ships a hosted remote cache backed by R2 and integrated with their developer platform, it competes with Nx Cloud in a Cloudflare-centric stack.

**v2.10.5 (July 13, 2026) -- MAJOR: Experimental Rust/Cargo workspace support**

This is Turborepo's first serious move beyond JS/TS. Key additions:

- **Experimental Rust/Cargo workspace support:**
  - Native Cargo workspace detection and task inference
  - Embedded sccache (bundled with turbo; no separate installation) -- "Cargo compile cache needs no installation"
  - Turbo Remote Cache exposed as sccache backend for Cargo tasks -- Cargo build artifacts route through Turbo's existing remote cache infrastructure
  - Cargo cache isolated by host platform (cross-platform cache correctness)
  - Cargo build environment inputs hashed for cache keys
  - Cargo prune Docker lockfile synchronization
  - Runs Rust workspace tests via nextest through task command override
  - Experimental Rust Guide added to docs
- **Task command overrides:** `command` field added to task configuration; allows overriding the actual shell command executed (separate from the task definition). Used for nextest integration.
- **Output path traversal fix:** `fix: Reject output path traversal` -- security fix, same class as prior cache hardening patches.
- **Incremental cache reuse reporting:** Cache summary now reports when incremental cache artifacts are reused (not just full task cache hits).
- **TUI text selection beyond viewport:** Continuous scrolling selection in task output.
- **Allow outputs outside package roots:** Required for Cargo (outputs go to `target/`).
- CI/CD: OIDC token exchange for Remote Cache authentication; Turborepo dogfoods its own Cargo support internally.

**v2.10.6 (July 22, 2026) -- Cargo-only repos + boundary enforcement + security**

- **feat: Support Cargo-only repos** -- Turbo now works in repos with no JS packages at all. Pure Rust repos with Cargo workspaces are now a supported use case.
- **feat: Infer Cargo workspace tasks** -- Turbo automatically generates task definitions for standard Cargo commands (`build`, `test`, `check`, etc.) from the Cargo workspace manifest. No `turbo.json` configuration needed for basic Rust workflows.
- **fix: Check dynamic imports in boundaries** -- Module boundary enforcement now flags dynamic imports (`import()`) in addition to static imports. Relevant to `turbo build`'s code isolation guarantees.
- **fix: Resolve weekly security audit vulnerabilities** -- Weekly supply-chain scan findings patched.
- **chore: Update to Rust 1.97.0** -- Internal Rust toolchain upgrade.
- Multiple Cargo-specific fixes: artifact caching, target output layout resolution, Cargo profile outputs, production workspace dev dependency pruning, Yarn Babel extension preservation.
- VS Code extension: macOS runner pin, type check inclusion.

### Key changes by category (July 7-27)

- **Features:** Rust/Cargo experimental support (MAJOR), task command overrides, Cargo-only repo support, Cargo task inference
- **Performance:** Output path traversal rejected earlier in pipeline; incremental cache reuse tracking
- **DX:** TUI viewport selection, embedded sccache (zero-install Cargo caching)
- **Security:** Output path traversal rejection (v2.10.5), weekly supply-chain audit (v2.10.6)
- **Ecosystem:** Cargo/Rust as first non-JS toolchain; nextest support; OIDC auth for Remote Cache
- **AI:** None. `experimentalCI` object remains undocumented (17+ weeks).

### Nx implications (updated July 27)

**Threat level: HIGH (sustained, new dimension added).**

1. **Turborepo is no longer JS/TS-only.** This is the biggest competitive shift in the July cycle. Turbo's experimental Rust/Cargo support directly challenges Moon's polyglot positioning. More critically, it extends Turbo Remote Cache value to Rust shops -- Turbo's existing remote cache infrastructure now serves Cargo builds. This is the "one cache, all languages" pitch.
2. **Nx has no first-party Rust/Cargo support.** There is a community `nx-cargo` plugin but no official `@nx/rust` package. As Turbo ships Rust support, Nx falls behind on the polyglot narrative. **Recommended: fast-follow with an official `@nx/cargo` or `@nx/rust` package, even if thin.**
3. **sccache integration is clever architecture.** Rather than building a new Rust-aware task runner, Turbo routes Cargo through sccache and exposes its existing Remote Cache as the sccache backend. This is lightweight to build and immediately leverages Turbo Remote Cache. Nx Cloud could do the same: expose an sccache-compatible endpoint.
4. **3.0 is dead or rebranded.** Now 17+ weeks since the "preparing for 3.0" blog. v2.10 is the cadence. Remove from watch queue.
5. **Dynamic import boundary enforcement** is a signal Turbo is hardening its module architecture/bundling story -- relevant if they're building toward code-ownership enforcement at build time.
6. **Local cache eviction (cacheMaxAge/cacheMaxSize from v2.10.0)** is still an Nx gap -- no change this cycle.

## Bazel

**Latest LTS:** v9.2.0 (July 13, 2026)
**Prior latest at July 6 snapshot:** v9.1.1 (June 3, 2026)

### Released since July 6

**v9.2.0 (July 13, 2026) -- Stable release**

- **TCP keepalive now enabled by default for gRPC connections** -- improves reliability of remote execution and remote cache connections in environments with aggressive firewalls or NAT timeouts. This was previously opt-in.
- **SOCKS proxy support** (`socks://`, `socks4://`, `socks5://` URLs) -- enables Bazel in corporate networks with SOCKS proxies. Enterprise usability improvement.
- **Performance regression fix:** Fixed `RepoMappingManifest` actions consuming excessive CPU time (regression introduced in Bazel 9). This was a notable performance blocker for large multi-module builds.
- **Parallel CDC chunk transfers within large blobs** -- faster remote cache upload/download for large build artifacts.
- **Removed gRPC message size limitations from remote executor** -- allows larger artifacts to pass through the remote execution layer.
- **`exec_properties` respects `resources:cpu` and `resources:memory`** for local resource estimation (previously these only applied to remote execution).
- **`module_extension()` now accepts `facts_version`** parameter for schema changes -- better Bzlmod compatibility.
- **New `and_then` method on transitions** to compose Starlark and native transitions.
- **`strip_components` attribute** added to `extract`/`download_and_extract`/`http_archive`.
- **Windows:** Fixed long-path executable execution issues; added UAC manifest to Windows launcher stubs.
- **SOCKS proxy** support for `socks://`, `socks4://`, `socks5://` URLs in external dependency fetch.
- Fixed symlink materialization and cross-repo symlink issues.
- Eliminated refetching of external repos when using hermetic Linux sandbox.

### Nx implications

**Threat level: Low (unchanged).** The TCP keepalive default and SOCKS proxy support are enterprise quality-of-life improvements that make Bazel easier to run in locked-down corporate environments. The `RepoMappingManifest` CPU regression fix may unlock adoption that was blocked by the performance hit. No JS/TS crossover. No direct Nx relevance, but Bazel's improved remote-exec reliability sets a higher bar for remote caching quality.

## Cross-Competitor Themes (updated July 27, 2026)

1. **Polyglot is no longer Moon's differentiator alone.** Turborepo's experimental Rust/Cargo support (v2.10.5/v2.10.6) is the biggest narrative shift this cycle. Turbo is no longer "the JS/TS-only tool." By routing Cargo builds through its existing Remote Cache infrastructure (via sccache), Turbo extends its value proposition to Rust shops with minimal architectural change. If Turbo follows with Go, Python, or JVM support, Moon's core differentiator collapses. The polyglot narrative is now a three-way contest: Moon (strongest, stable), Turbo (experimental Rust), Nx (JVM partial, no first-party Rust).

2. **Bazel RE protocol is becoming a remote cache interoperability standard.** Moon v2.4's Bazel RE gRPC support means Moon can plug into Depot, BuildBuddy, and Bazel-compatible cache infrastructure. Bazel 9.2.0's improved remote cache reliability reinforces this ecosystem. Nx Cloud is not Bazel RE-compatible; it uses a proprietary protocol. As enterprises consolidate on Bazel RE as the standard remote cache protocol, this becomes an Nx Cloud positioning question.

3. **Automatic vs. explicit task configuration is the DX battleground.** Vite+ (auto input fingerprinting), Turbo (Cargo task inference, deferred input hashing from v2.10.0), and Moon (dependency-aware scheduling) are all pushing toward zero-config or lower-config task definition. Nx requires the most explicit configuration of the three major JS tools. This framing will dominate "Turbo vs Nx" evaluation posts.

4. **Local cache management is now a Turbo differentiator.** `cacheMaxAge`/`cacheMaxSize` from v2.10.0 remains an Nx gap. No progress from Nx this cycle.

5. **Cloudflare + Vite+ = potential remote cache threat.** No new announcement this cycle (source blocked), but the product surface remains obvious. Carry forward from July 6.

6. **Turbo 3.0 is confirmed abandoned.** 17+ weeks from the "preparing for 3.0" narrative with no RC. v2.10.x is the reality. Remove from watch queue.

7. **Rust toolchain upgrades are synchronized across the ecosystem.** Both Turbo (1.97.0 in v2.10.6) and Pants (1.97.0 in dev releases) upgraded to Rust 1.97.0 in the same two-week window. This is routine but confirms the ecosystem is aligned on the Rust release train.

### Where Nx Is Behind

- **Rust/Cargo polyglot support:** Turborepo now has experimental Rust/Cargo support; Moon has stable polyglot. Nx has no first-party Rust package.
- **Bazel RE remote cache interop:** Moon v2.4 plugs into Depot/BuildBuddy via the Bazel RE gRPC protocol. Nx Cloud uses a proprietary protocol.

- **Cache security audit:** Turbo patched path traversal in v2.10.5 (a second cache security fix this cycle). Nx has not publicly confirmed auditing the same classes (6+ weeks overdue).

### Where Nx Is Ahead

- **Distributed Task Execution:** No competitor ships DTE. Turbo's `experimentalCI` is 17 weeks undocumented.
- **Nx Cloud:** Remote caching with security controls, observability, and managed CI orchestration. Vite+ has no cloud product. Moon has no cloud product.
- **Nx Console:** Turbo contracted scope (web UI removed, v2.9.18). Nx Console remains the richest IDE-integrated monorepo experience.
- **Generator ecosystem breadth:** Nx generators (create-nx-workspace, @nx/* plugins) vastly exceed Moon's templates and Vite+'s current scaffold story.

### Unassailable Moats

- **DTE + Nx Cloud:** Architectural decision requiring distributed coordination infrastructure. No competitor can replicate with a single release.
- **Workspace generator ecosystem:** Decade of community plugins and official generators.
